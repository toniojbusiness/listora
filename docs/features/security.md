# Security review

This review covers the whole codebase on `main` as of 2026-10-25: auth and tenancy, secrets,
webhooks and email ingest, input validation and SSRF, the browser runner, infrastructure,
dependencies, and the iPhone app. It lists what was found, how severe it is, and what was done
about it. Every high and medium finding is fixed, except one medium that cannot be exploited
until public sign-up opens (row 7); it must ship with T-31. Low findings are follow-ups.

Severity: **high** means exploitable from the internet today. **Medium** means exploitable with
some precondition, or a gap with real impact. **Low** is defense in depth.

## Checked and fine

- **Tenancy.** Every `/v1` route goes through `contractRoute`, which authenticates before the body
  is read and hands the handler a `Tenant`; every repository query filters on its account
  (checked across items, photos, uploads, listings, operations, tasks, sales, profit, today,
  connections, and marketplace sessions). The only routes outside the contract are health, the
  dev auth routes, the local storage driver (HMAC-signed), the eBay webhook (signature), and the
  OAuth callback (state).
- **Secrets.** OAuth tokens and browser sessions are sealed with KMS envelope encryption bound to
  a purpose, never returned by the API, and redacted from logs. The Anthropic key and the
  database password reach the containers only as ECS secrets from Secrets Manager. A scan of
  the current tree and the full git history found no credentials, only the fakes' test values.
- **Webhooks.** The eBay signature is required on every notification and checked over the exact
  bytes; a key that cannot be read answers `503`, never accepts. Notifications are deduped by a
  unique constraint in the same transaction as their effects. Depop's verifier (HMAC over the
  timestamp and raw body, constant-time compare, a 5-minute window) is correct but not yet
  routed.
- **Input.** Fastify's 1 MiB body limit, 256 KiB on the webhook; every request string and array
  in the contract has a size cap; upload targets sign the content type, exact length, and
  checksum. No user input reaches SQL text, a shell, or a file path. Storage keys are
  server-generated. Server-side fetches go only to fixed or configured hosts (no user URL is
  fetched), and the OAuth callback redirects only to the app's own scheme.
- **Automation.** Script navigation is held to the profile's origins; CAPTCHAs, bot checks, and
  verification steps stop the run and hand the step to the user; no tracing, HAR, or page
  capture; downloads and popups are off; session cookies are limited to the marketplace's
  domains when linked, loaded, and rotated.
- **Infrastructure.** Both buckets block public access and require TLS 1.2; RDS is in isolated
  subnets, not publicly accessible, encrypted, with `rds.force_ssl` and verified TLS; security
  groups admit only the load balancer to the API and only the services to the database; the ALB
  redirects HTTP to HTTPS with a TLS 1.2+ policy; task roles' KMS, S3, and Secrets Manager
  grants are scoped to their own resources and purposes; containers have read-only root
  filesystems.
- **Dependencies.** `npm audit` reports no vulnerabilities.
- **iPhone app.** The session token is a Keychain item (`AfterFirstUnlockThisDeviceOnly`), never
  in UserDefaults or files; App Transport Security exceptions exist only in the Dev
  configuration; the bundle holds no secrets; the marketplace sign-in view uses a non-persistent
  data store and keeps captured cookies in memory only. It opens a pasted or shared sign-in
  link only on the marketplace's own domains over https; a shared one waits in the Keychain
  (`AfterFirstUnlockThisDeviceOnly`) only until the sign-in page takes it or closes.
